# 对话总结与设计共识

整理日期：2026-10-09。依据本次项目对话及仓库现状整理，是工作摘要，不是聊天逐字备份。

用途：让用户和之后接手的开发者在没有旧聊天、截图临时文件的情况下，仍能理解“为什么这样做、哪些已经改过、什么不能倒退”。运行、当前分支和后续任务见 [换机交接](./后续任务与换机交接.md)。原始文件按原文归档，不把原稿里的全部设想说成已经上线。

## 1. 最重要的一次方向纠正

用户想做的主场景一直是**站内地图赶路**：

> 下地铁的时候前面总有人挡住，坐电梯的时候有些人下了电梯就站在电梯口，横冲直撞的小孩，安检非常慢，人工窗口不开。

核心感受是“我一直想冲，但总有人阻碍我”。曾经实现偏成固定路线、三跑道避障和问答页，用户明确指出这不是原本想法。后来改回地图中沿通道移动、遇到真实阻碍、借过／绕行／等候／完成操作后继续赶路。

“一直想冲”是急迫感，**不等于一直按住冲刺就该成功**。大学生无脑持续冲刺应失败；聪明地分段冲刺、读牌、看队伍和处理事件才有收益。小人要有明显奔跑、疲惫、被挡住和恢复的动作，不能让用户只看着等，也不能用不断弹选择题代替地图互动。

## 2. 用户反复强调的界面要求

- 手机优先。操作出现时固定在底部，按钮大，允许遮挡部分地图；一次操作不能要求上下滑动找按钮。这一点曾出现回退，是重点回归项。
- 每次都要清楚知道“我在做什么、下一步按哪里”。开始前、赶路中、被挡住、排队中、轮到自己和放行后要有不同反馈。
- 连续任务不能看起来只是同一页换了一句字。步骤、前一题选择结果、场景和动作应有明显变化。
- 人物在开局左上，以卡通人物和说话气泡表达“我一定会赶上这趟车”；开始按钮首屏易见、易按。
- 人物选择横向滑动，难度用“简单 1 星”等文字和星级，不写生硬的“难度 1/5”。
- 初始选项同色，不能把第一项预先染成已选中或正确答案；选中之后才反馈。
- 扣时写成醒目的红色“−30 秒”，不要“−0:30”。体力、专注、精力上限等负面代价也应放前面并醒目，不能只突出时间。
- 删除“无事发生／不花时间／不额外扣时间”一类无意义提示，用具体处境和结果代替。
- 不向玩家显示隐藏概率，也不要把尚未发生的随机后果直接剧透成标准答案。误导选项要有吸引力，同时方向题应能凭游戏内线索判断。

## 3. 人物与解锁

新玩家先用大学生，成功后依次解锁打工人、疲惫游客、带娃家长。通关资格永久保留，之后失败不能把已经解锁的人物锁回去。用户曾发现失败回锁的问题，之后一直是回归重点；换电脑没有本地存档是另一个问题。

| 人物 | 已确认的背景与体验 |
| --- | --- |
| 大学生 | 精力和手机电量高，觉得来得及；朋友家的沙发舒服／咖啡店小猫可爱，随机出现。要保留“高电量、高精力”的说明。书包乱、证件需要找；不应出现打工人的工作群背景。 |
| 打工人 | 妈妈舍不得自己走，但必须回去上班，妈妈还塞特产；老板持续催。老板消息用“之前那个设计稿／测试版本／报价，今晚能发吗？”，回答“今晚一定发”消耗体力，或不理，之后可能来电话。 |
| 疲惫游客 | 必须回家上班，在陌生地方碰壁，精力低、疲劳高、手机电量低的形象。地铁可以设闹钟补觉；睡着后跳到叫醒的那站，再由玩家决定是否下车。不能还没出发就显示已经被提前叫醒。 |
| 带娃家长 | 管理自己和孩子的体力、耐心、尿意与牵手距离；厕所、零食、抱娃、等孩子都会改变后续局面。保留没有道具也能继续的处理方式。 |

“出行家庭／婴儿车家庭”的原始设计稿已经一起收录，但仍是后续角色规划，不要仅因文档存在就宣传已实现。

## 4. 六站固定特色

以下是游戏里的剧情人物和抽象地图设定，不用于现实交通导航。

| 车站 | 用户确认或接受的方向 |
| --- | --- |
| 郑州东 | 老乡多、爱搭话，中央大厅与对称两翼容易看错编号。打工人被问工资：不告诉会纠缠；告诉后可说真话或报低工资，引出借钱／嘲讽。该对话仍有数值取舍不足，不能悄悄改写用户指定的故事。 |
| 上海虹桥 | 长距离、长廊和近路／外侧通道；老太太嫌弃所有人，形成稳定角色性格。 |
| 杭州东 | 返工和通勤氛围，出发与到达岔路。带娃家长知道左边近电梯上个月坏了，右边远但可靠；方向线索必须提前给，不能要求玩家熟悉杭州。 |
| 武汉 | 换层、认出发层；剧情里的小卖部老板和遇到的人急躁，孩子反复喊妈妈买周黑鸭。 |
| 北京南 | 安检最严格，观察队伍、按流程处理物品；家长带的水壶零食也有操作差异。 |
| 广州南 | 路远、人挤、换层，热心指路却意见不一；路上到处是被抱着的孩子，自己的孩子也一直要抱。 |

同一个车站对不同人物应有不同处境和解法，不是所有角色只改名字、再把罚时乘大。

## 5. 几个需要保留的具体选择

### 大学生的小蛋糕

奶茶选择已被用户改成“朋友打包好的小蛋糕，要不要带上”。随后又明确纠正：蛋糕必须拎着，要保护，不能凭空加体力。

当前约定是：带上扣 75 秒、专注 +5、负重 +5，占手并增加一路保护的体力消耗；不带则伤心分别、专注 −5。不能退回旧版“带上体力 +10、不带无事发生”。

### 证件与早餐

不提前查证件的答案改为“先跑到检票口再说吧”，后果是需要自己翻包，而不是强调现在免费。早餐两项要展示各自代价，包括后续精力上限下降。最新修复缩短整理和吃饭耗时，并让空腹真正影响赶路，详见第 7 节。

### 没听清地铁报站

用户明确给过取舍：去门口等，体力 −5、时间 −5；继续坐着，时间 −5，可能错过站再损失 50 秒。具体风险由内部设定，不向玩家显示概率。不能把两个选项设计成只比谁少扣一点时间，或把隐藏结果提前说死。

### 安检和阻挡

排队不能只是静态 A/B/C 人数；其他队伍也应随时间变化，换队要实际排到新队后面。轮到自己以后要知道当前是在放包、检查还是放行。孩子横穿造成的耽搁需要醒目的时间反馈。等待可以存在，但玩家要知道为什么等、还能做什么，并看到人物反应。

## 6. 从早期数值问题到新的原则

最早约 3–5 位朋友试玩，普遍按住冲刺，第一关还能剩约 500 秒。用户认为太容易，希望大学生首次通过率约 75%，之后逐级更难。

后来提出每局至少 12 次有效操作，途中可以提示肯定赶不上，但必须比较剩余时间与真正的最短所需时间。不能拿平均用时判断“必败”，更不能用错误估计提前终止仍可救回的局。

双方最后对齐的计时公式：

```text
开局可用时间 = 正常地铁行程 + 站内赶路 + 必要操作 + 预计环境耽搁 + 犯错余量
```

先算各人物、各站正常完成需要多少时间，再用 **240／180／135／90 秒**容错区分人物。取消简单把角色罚时统一放大的方案。车站仍通过路线、剧情、操作和资源需求体现差异。

排队、睡觉和安检不能重复扣时；显示日志不是再扣一次。每次改变正常流程成本，要重测基线，不把准备变便宜后省出的时间无声变成额外宽松。

事件必须有状态相关的选择价值。不能固定第一个扣时间、第二个免费，也不能所有角色所有站都一眼选出最快答案。另一方面，合理误导需要可观察线索，不能靠不读懂的城市常识或不可预见的巨额随机罚款制造难度。

## 7. 最近已经实际完成的工作

这里列出的是可由提交和测试报告核对的阶段成果，不代表所有设计目标已验收。

| 提交 | 工作 |
| --- | --- |
| `9d6a228` | 实际时间账本及重复计时核查 |
| `3ae6fd3` | 明确参考玩家并测正常完成耗时 |
| `9b8e92c` | 接入 240／180／135／90 秒容错，撤掉角色统一方向罚时倍率 |
| `81f1c20` | 控制冲刺加速，大学生久冲掉速，验证分段冲刺和持续乱冲 |
| `f92b217` | 分析准备收益、路线取舍、读题罚时，发现早餐／咖啡不值及读题惩罚突增 |
| `fedc5fc` | 修普通读题罚时、准备收益及开局基线 |

最新修复重点：

- 普通读题和操作只扣自然时间，不再额外罚几十秒或替玩家自动选答案；闹钟和报站的实际错过窗口仍保留。
- 身份证整理 10 秒；大学生和打工人吃饭各 20 秒；游客咖啡 20 秒、短休 8 秒、调整箱轮 6 秒。
- 大学生空腹到大厅后降低精力上限且移动稍慢；打工人空腹在站内拖箱子稍慢。效果有文案提示，不是隐藏追加扣款。
- 新正常基线冻结后，四人物平均检票余量仍对应既定容错。
- 394 项自动测试和构建通过，768 次正常参考流程完成，384 次大学生持续乱冲压力场景全部失败。普通读题额外固定罚时核查为 0。

这些是固定策略工程验证，不能当作“真人首次通过率已经达到 75%”。上海家长慢读仍有少数场景失败，环境预算、混合错误模型和真实触控试玩还要继续。

## 8. 结算、分享和资料

用户提供了结算与成就设计，项目已有称号、长期解锁、成就及分享入口。分享后别人能打开游戏继续玩，不只是发一张图。

失败主提示不要展示“按剩余路程估算还差 533 秒”等生硬数据。根据差距表现“错误太多”“下次吸取教训”“就差一点点”，允许同档多条文案；技术明细与简短情绪反馈分开。大约 100 秒内、100–200 秒、差更多，是用户给过的分档方向，后续以对应实现核对，不应把主屏重新做成算式报表。

已归档资料包括：整体玩法、事件系统、六站地图、大学生／打工人／游客、家长与家庭、结算与成就、数值平衡与通过率。资料索引在 `docs/design/README.md`。用户曾要求把原始文档整理进仓库，后续分析和实施文档也已单独保留；不要覆盖原稿造成无法追溯。

## 9. 协作和发布习惯

- 用户希望直接推进已经授权的工作，少问重复确认；但发布版本和开发修复要分清。
- “继续”通常是继续当前任务，也要把中途新截图和纠正合并到正在做的工作里。
- 改动要同时改实际逻辑与界面说明，并自测；曾多次出现用户仍看到旧文案，要核对分支、服务目录、浏览器入口和实际构建。
- 用户明确反对每次修复都推一个新 beta。沿用修复分支，积累并验收；正式发布再按分支／PR／tag 流程处理。
- 给朋友测试时需要能打开的链接。推送不等于部署，工作流成功和测试入口内容需核验；曾发生过 404。
- 已分享出去的正式链接要继续可用，测试版不能随意覆盖正式版。
- 仓库备份不等于聊天和浏览器存档备份。为避免依赖旧电脑，本次把讨论共识和后续安排写成这两份文档；新对话可直接按交接入口继续。

## 10. 接手时不要得出的错误结论

- 不要因旧 README 或历史代码出现 runner，就认为目标仍是三跑道跑酷。
- 不要因家长／家庭原稿已经上传，就认为所有家庭角色已完成。
- 不要因当前普通参考流程全过，就宣称真人通过率已达标。
- 不要因样本环境损失没超过 75 秒，就宣称已经实现环境硬上限。
- 不要把原角色罚时倍率、旧开局时间或“普通超时自动扣款”重新加回来。
- 不要让读题、准备与地铁喧宾夺主；地图里急着跑、被挡、主动处理、又跑起来，始终是主要体验。
