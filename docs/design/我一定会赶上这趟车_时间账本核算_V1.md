# 时间账本核算 V1

日期：2026-10-09。范围：核算当前规则的初始预算与实际扣时，为下一步数值校准提供依据。

本文补充《数值实施对齐与改动计划 V1》的第一步。当前没有把目标通过率当成已达成结果；不在这一步调整角色容错、冲刺罚时、事件概率或地图距离。

## 1. 先分清两只时钟

- **屏幕上的检票剩余时间**：到停止检票还剩多久。
- **内部发车剩余时间**：在检票剩余时间之上，还包含停止检票至发车的 180 秒。

因此，进入游戏时有 `内部剩余 = 屏幕检票剩余 + 180`。过检票前，内部剩余到 180 就失败；已经过检票后，继续使用剩下的发车时间。不能把这 180 秒误当成玩家在检票前可用的容错。

账本必须分别统计检票前和检票后的扣时。过检票时应满足：

```text
检票时余量 = 初始检票预算 − 检票前累计扣时
内部实际耗时 = 初始内部剩余 − 当前内部剩余
内部实际耗时 = 账本每项之和 = 检票前累计扣时 + 检票后累计扣时
```

失败局只统计到失败发生为止。其账本不能当成完成全路线所需时间。

## 2. 初始预算与实际消耗分别核对

初始预算回答“开局给了多少时间、每一部分从哪里来”；实际账本回答“玩家这一局把时间花在哪里”。两者分开记录，避免把原先含有各种开销的缓冲字段直接改名为纯容错。

初始预算输出四个人物、六站、普通及极限共 48 组。每组保留未取整的组成项、取整差额、极限扣减、检票预算和 180 秒发车保留量，由游戏实际创建函数产生，不在报告脚本复制另一套计算公式。

实际账本由真实游戏 reducer 逐次记录扣时；路线选择、准备操作、排队、读题、事件选择、睡眠与路线进度等都经过同一条记账入口。日志中的剧情说明不是账本：它可能只记录事件罚时，没有记录其间正常流逝的时间。

睡眠尤其需要区分两件事：睡着时推进地铁进度，对应的车程仍然过去；不能在车程之外再重复增加一笔“睡觉罚时”。安检也要分清正常排队、操作耗时和误判额外耽搁，不能把三者都叫作倒霉。

## 3. 本次审计场景

命令：

```sh
PATH=/opt/homebrew/bin:$PATH npx vite-node scripts/timeAudit.ts > artifacts/time-audit.json
```

默认使用固定随机种子 `921`，每个角色、每个站、每种难度执行以下五种场景，共 **240 局**：

| 场景 | 用途 |
| --- | --- |
| 默认准备，分段冲刺 | 当前审计驱动的基础对照 |
| 默认准备，全程步行 | 检查移动时间和自然恢复的记账 |
| 默认准备，持续冲刺 | 检查岔气与疲惫事件扣时 |
| 省时准备，分段冲刺 | 检查准备成本、后续属性和事件变化 |
| 默认准备，一次方向误判，分段冲刺 | 检查误判扣时和路线改变 |

分段冲刺沿用现有脚本的“冲 4 秒、走 3 秒”，体力、冲刺负荷或孩子距离达到阈值时提前走路；读题使用 5 秒。它是测试输入，不是新版参考玩家的冲刺占比。

默认准备分别为：大学生不带蛋糕、检查证件、吃饭；打工人带土特产、吃饭、回复老板；游客喝咖啡、带纪念品；家长先带孩子去厕所、带零食。省时准备分别为：大学生都跳过；打工人不带土特产、不吃饭、不回复；游客直接走、减轻行李；家长直接走、不带零食。

需要增加随机覆盖时使用：

```sh
PATH=/opt/homebrew/bin:$PATH npx vite-node scripts/timeAudit.ts --seeds=921,1004,1087 > artifacts/time-audit.json
```

这会执行 720 局。不同策略使用相同种子便于比较，但策略引起的事件分支仍可能改变后续随机调用顺序，不能把两个分支当成完全相同的遭遇。

## 4. 报告怎么读

脚本输出以下数据；本轮实际运行结果见第 6 节及 [审计报告 JSON](./time-audit-report.json)：

- `initialBudgets`：48 组初始预算的分解，覆盖普通和极限。
- `actualSpent`、`accounted`、`ledgerTotal`：倒计时实际减少量、账本逐项求和、账本累计总量，三者必须一致。
- `beforeGate`、`afterGate`、`gateMargin`：检票前后扣时与真实过检票余量。没有过检票的局不伪造余量。
- `categories`、`entries`：按扣时类型汇总，以及可追溯到来源、阶段、检票前后的明细（加 `--details` 输出逐项明细，默认保留汇总以控制报告体积）。
- `elapsedRealSeconds`、`ledgerRealSeconds`：真实操作秒数，避免与加速后的游戏秒混用。
- `clippedByDeadline`：失败时截断的账本；`notCompleted`：审计驱动异常而没有产出完整结果。
- `actualNavigationMistakes`：实际触发的方向误判数量，不把要求脚本误判一次当成必然已经发生一次。

记账容差为 0.001 秒，用于浮点运算误差。倒计时对账错误、检票余量对账错误、真实秒数不一致、出现未分类扣款或驱动未完成，均令脚本以失败状态退出。

## 5. 这一步可以得出的结论与边界

通过审计后，可以确认被覆盖场景的每一秒都能追溯到来源，并找出预算公式与真实过程之间的差额。不能仅凭账本守恒就说预算合理：重复收费如果被完整记账，账本仍然能对上，因此还必须结合睡眠、排队、安检和过检票边界的专项测试。

本脚本知道路线和队列答案，默认会提前靠门、处理事件。它适合核对计算，不代表首次游玩的普通玩家。报告中的通关与失败只标识账本是否走完全程，不用于宣传通过率，也不证明所有随机局都可通关。

下一步才是在这套账本上定义正常完成参照：必要耗时、玩家主动付出的成本、可避免的失误、不可控额外耽搁分别统计，再加入独立容错预算。人物目标通过率与随机环境 35／75 秒目标仍按实施对齐稿后续验证。

## 6. 本轮实算结果

实现基线为 `7f131ab` 加本次时间核算改动。执行 3 个固定种子 `921 / 1004 / 1087`，共 **720 局**，覆盖 4 人物 × 6 站 × 2 难度 × 5 行为。

- 720 局均完成到通关或截止失败，没有驱动异常。
- 逐项扣时总和与实际倒计时、检票前后余量、真实操作秒数全部对齐，最大误差小于 0.001 秒。
- 未分类扣时为 0；失败时的最后一帧及即时罚时也保留，没有为凑平账而截去。
- 354 局完成、366 局截止失败，仅用于说明审计走到了哪些边界。这些刻意包含持续冲刺、全程步行和极限模式的用例不能合并解释为游戏通过率。
- 48 组开局时间均与改动前一致。本次没有更改容错目标、冲刺罚时、地图距离或角色速度。

### 6.2 当前开局公式的真实含义

```text
当前可见时间 = 向上取整到 30 秒（旧地铁基准 + 旧站内步行分配 + 旧混合缓冲）− 极限扣减
```

已将四个人物接入统一计算函数 `buildTimeBudget`，记录每项输入与取整差额。旧混合缓冲仍明确命名为 `legacyAllowanceSeconds`，必要交互、预计环境、纯容错标为未校准（`null`），不伪装成已经拆分完成的新公式。旧步行分配也包含检票后的上车段。

例如大学生杭州：

```text
旧地铁基准 646.67 + 旧步行分配 276 + 旧混合缓冲 150
= 1,072.67 秒
向上取整补 7.33 秒 → 开局 1,080 秒（18:00）
```

同站、普通模式、种子 921、默认准备与分段冲刺，在实际引擎中：

| 检票前实际支出 | 游戏秒 |
| --- | ---: |
| 地铁乘车及路线内步行 | 641.49 |
| 检查证件和吃早餐的固定成本 | 90.00 |
| 读题和操作 | 80.86 |
| 站内实际移动 | 153.60 |
| 到站判断及动画交界剩余帧 | 2.00 |
| 正常安检队列 | 19.00 |
| 等人让路 | 5.11 |
| 其他选项固定成本 | 4.00 |
| 合计 | 996.06 |

所以检票前余量是 **1,080 − 996.06 = 83.94 秒**，不是旧 buffer 标的 150 秒。检票后的 **35.44 秒**另列，不能再减一次检票前余量。表内分项保留两位小数，合计由未取整值计算。

## 7. 已修复和仍需校准的项目

本次已修复：

1. 地图延迟帧在内部拆成小帧后，外层又记一遍旧学生账本的问题。现在分帧发生在统一记账入口前，同样操作的大帧与小帧只计一次。
2. 选定地铁路线后，剩余行程预估随人物疲劳、负重改变而漂移的问题。现在选线时冻结乘车、步行、换乘固定成本；实际扣款和同一路线的剩余预估共用冻结值。选线前的准备仍会影响选线时的成本。
3. 只有大学生可核对完整时间的缺口。四个人物均有统一账本，按阶段、来源、检票前后归档；准备成本、计时流逝、事件固定成本分别记录。

确认没有重复扣款：游客睡觉跳站只消耗推进的车程；安检完成日志只展示已经扣过的队列时间；小孩扣时动画也只展示实际耗时；北京旧放托盘任务已跳过。额外开包检查是不同事件，不误删。

仍需在后续参考模型中解决，暂不偷偷改变难度：

- **开局地铁估算与实际步速不一致。** 学生旧基准按速度 1，实际初始约 1.02336；家长旧基准按 .94，实际初始 .98。具体偏差见 JSON 的 `legacyMetroOverAllocation`。仅纠正这一项会令家长北京、武汉开局各减 30 秒，其余现有组合因取整不变。本次保留旧输入作为对照。
- **站内 walking 包含检票后路程。** 下一步必须拆出检票前参考移动，检票后单独校验 180 秒窗口。不能把整个 walking 都当成检票前必须花费。
- **正常安检不等于随机坏运气。** 新账本单列安检排队；旧 `student.environmentLoss` 仍是历史统计，不能用它直接实施 75 秒纯环境上限。
- **自动脚本不是无误差玩家。** 当前非学生翻证件阶段，脚本在找钱包与拿证件两步各读题 5 秒、操作 1.5 秒；第二步 6.5 秒超过 6 秒时限，确实被罚 35 秒。账本已将它归为 `operationPenalty`，不会再被误认为正常移动或环境损失。下一步定义参考玩家时必须明确读题与执行时长。
- **固定事件成本和交互仍需逐项解释。** 例如放包、开包、换乘操作与路线本身的步行是不同支出。账本记录真实收了多少，不用守恒测试代替对事件本身是否合理的判断。
