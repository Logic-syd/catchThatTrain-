# 《我一定会赶上这趟车》结算与成就系统设计文档

版本：V1.1  
用途：供产品设计与 Codex 开发实现  
范围：仅包含单局结算、称号、副标签、失败/成功原因分析、长期成就与相关数据结构。地图系统另行设计。

---

## 1. 系统目标

结算页不能只展示“赶上 / 没赶上”和流水账数据。

它需要同时回答四个问题：

1. 这局结果是什么？
2. 玩家为什么赶上 / 为什么没赶上？
3. 这局最有记忆点的经历是什么？
4. 玩家下一局可以怎么做得更好？

整体结构：

**单局结果 → 主称号 → 副标签 → 关键原因分析 → 详细数据 → 长期成就**

核心原则：

- 主称号负责“记忆点”
- 副标签负责“快速概括”
- 原因分析负责“复盘”
- 详细数据负责“验证”
- 长期成就负责“重复游玩动力”

# 2. 结算页信息层级

## 2.1 顶部：结果 + 主称号

成功示例：

> 赶上了  
> **压哨上车王**  
> 距离停止检票：00:07

失败示例：

> 没赶上  
> **身份证去哪了**  
> 距离检票口：43 米

主称号必须比详细数据更显眼。

## 2.2 第二层：副标签

每局最多展示 3 个。

示例：

`#零走错` `#最后冲刺` `#身份证秒找到`

失败：

`#体力见底` `#安检误判` `#多跑了210米`

副标签要短、直观，不写完整句子。

## 2.3 第三层：为什么赶上 / 为什么没赶上

成功：

### 这局你为什么赶上了

- 提前检查身份证，约省 28 秒
- 选对安检队，约省 31 秒
- 最后一段冲刺追回约 24 秒

失败：

### 这局你为什么没赶上

- 走错 B 区，多花约 54 秒
- 安检队伍判断错误，多花约 41 秒
- 前半程冲刺过多，最后体力耗尽

规则：

- 最多展示 3 条
- 优先展示“玩家可控制”的原因
- 环境随机因素放在次要位置
- 目的不是解释所有细节，而是让玩家知道下一局能改什么

## 2.4 第四层：详细数据

建议字段：

- 路线判断：A / B / C
- 走错 / 坐过站：X 次
- 主动选择额外用时：MM:SS
- 环境额外耽误：MM:SS
- 换乘表现：优秀 / 一般 / 较差
- 冲刺占赶路时间：X%
- 冲刺追回约：MM:SS
- 最终剩余 / 超时：MM:SS
- 角色专属数据

大学生：
- 身份证搜索耗时
- 翻错次数

游客：
- 地铁睡眠恢复
- 是否坐过站

妈妈：
- 孩子尿意最高值
- 是否发生罢工 / 尿裤子

家庭：
- 电梯等待耗时
- 无障碍绕行距离

# 3. 主称号生成规则

主称号不能随机发放。

推荐优先级：

1. 极端特殊事件
2. 极限成功 / 极限失败
3. 强人物专属结果
4. 强地图 / 场景专属结果
5. 最大成功原因 / 最大失败原因
6. 普通优秀表现
7. 默认称号

示例：

玩家最后 2 秒赶上车，同时路线判断也很好：

优先显示：

**最后一秒选手**

而不是：

“路线大师”。

# 12. 戏剧性指数 Drama Score

建议内部增加：

```ts
dramaScore: number
```

用于判断一局到底有多“离谱”。

以下情况增加 dramaScore：

- 走错路
- 坐反
- 坐过站
- 找不到身份证
- 孩子上厕所
- 孩子尿裤子
- 电梯长时间排队
- 地铁临停
- 最后 30 秒仍未到检票口
- EN 接近 0
- 连续选择高风险路线
- 中途失败概率很高后翻盘

示例：

- dramaScore < 20：非常顺
- 20–49：正常波折
- 50–79：明显混乱
- 80–99：极限逆风
- ≥100：灾难级赶车

推荐称号关联：

```text
dramaScore >= 80 && success
→ 一路翻车也赶上了

dramaScore >= 100 && success
→ 这都能赶上？

dramaScore < 15 && success && routeEfficiency >= 95%
→ 计划通
```

# 13. 时间影响记录 TimeImpact

所有会改变最终成绩的行为尽量记录为统一结构。

```ts
interface TimeImpact {
  id: string
  source: string

  category:
    | "decision"
    | "navigation"
    | "movement"
    | "character"
    | "environment"
    | "operation"

  deltaSeconds: number

  avoidable: boolean
  positive: boolean

  characterId?: string
  eventId?: string
}
```

示例：

```ts
[
  {
    source: "提前检查身份证",
    category: "decision",
    deltaSeconds: 28,
    avoidable: true,
    positive: true
  },
  {
    source: "选错安检队",
    category: "decision",
    deltaSeconds: -51,
    avoidable: true,
    positive: false
  },
  {
    source: "地铁临停",
    category: "environment",
    deltaSeconds: -30,
    avoidable: false,
    positive: false
  }
]
```

# 14. 成功 / 失败原因生成算法

## 成功

1. 筛选 `positive === true`
2. 按 `deltaSeconds` 从大到小排序
3. 优先选择 `avoidable === true` 的玩家主动贡献
4. 最多输出 3 条

示例：

> 你为什么赶上了：
>
> - 提前检查身份证，省约 28 秒
> - 安检队选对了，省约 31 秒
> - 最后一段冲刺追回约 24 秒

## 失败

1. 筛选 `positive === false`
2. 优先 `avoidable === true`
3. 按损失绝对值排序
4. 最多输出 3 条
5. 如果不可控环境损失非常大，可补充 1 条环境原因，但不要抢主叙事

示例：

> 你为什么没赶上：
>
> - 走错 B 区，多花约 54 秒
> - 安检判断失误，多花约 41 秒
> - 前半程冲刺过多，最后无法继续冲刺

# 15. 长期成就系统

长期成就与单局称号分开。

称号描述“这一局”。

成就描述“玩家已经完成过什么”。

建议状态：

```ts
type AchievementState = "locked" | "unlocked";
```

数据结构：

```ts
interface AchievementConfig {
  id: string
  name: string
  description: string
  hidden?: boolean
  category:
    | "general"
    | "student"
    | "worker"
    | "tourist"
    | "mother"
    | "family"
    | "station"

  condition: AchievementCondition
}
```

# 29. V1.1 补充：系统边界与术语

为了避免后续开发时“称号、成就、标签、复盘”互相混用，统一定义如下。

| 名称 | 生命周期 | 数量 | 用途 |
|---|---|---:|---|
| 主称号 Title | 单局 | 1 | 概括这一局最有记忆点的结果 |
| 副标签 Tag | 单局 | 0–3 | 快速说明这局发生了什么 |
| 原因分析 Factor | 单局 | 2–3 | 解释成功 / 失败的关键因果 |
| 长期成就 Achievement | 永久 | 多个 | 给重复游玩提供收集目标 |
| 隐藏成就 Secret Achievement | 永久 | 多个 | 奖励特殊、戏剧性的玩法 |
| Drama Score | 单局内部值 | 1 | 衡量本局混乱 / 戏剧程度，不直接作为成绩 |

重要规则：

- 同一句文案尽量不要同时作为主称号和长期成就名；确实很有梗的少数例外可以保留，例如“车赶上了，裤子没赶上”。
- 主称号必须描述“这一次发生了什么”。
- 长期成就必须描述“玩家已经完成过什么”。
- 副标签不要抢主称号的信息层级。
- 失败局也可以解锁成就。

# 30. 结果判定与 Margin

所有结算逻辑先统一出一个 `resultMarginSeconds`：

```ts
// 成功：正数，表示还剩多少秒
// 失败：负数，表示晚了多少秒
resultMarginSeconds: number
```

例如：

```text
+7   => 提前 7 秒赶上
-18  => 晚了 18 秒
```

同时记录：

```ts
interface ResultPosition {
  phase:
    | "metro"
    | "station_entry"
    | "security"
    | "concourse"
    | "gate"
    | "platform";

  distanceToGoalMeters?: number;
}
```

这样失败称号可以区分：

- 还在地铁里 → “下次真的早点出门吧”
- 卡在安检 → “栽在安检口”
- 检票口前 20 米 → “车门就在眼前”

不要只用 `success: boolean` 判断文案。

# 31. “为什么赶上 / 为什么没赶上”的关键因果算法

当前文档中的 TimeImpact 排序需要再加一层“是否足以改变结果”的判断。

## 31.1 失败局：找出真正的关键败因

假设玩家晚了 42 秒：

```text
resultMarginSeconds = -42
```

本局可避免损失：

```text
走错检票区      -54秒
买奶茶          -120秒
安检选错队      -31秒
地铁临停        -40秒（不可控）
```

不能简单说“奶茶损失最大，所以奶茶是主败因”。

更合理的规则：

1. 过滤 `positive === false`
2. 玩家可控因素优先
3. 判断单项损失是否 `>= abs(resultMarginSeconds)`
4. 满足时，标记为 `decisive: true`
5. 如果没有单项足够，则按损失从大到小累计，找出能够覆盖失败差值的最小因素集合

例如玩家晚 42 秒，走错检票区损失 54 秒：

> **关键败因：走错检票区。** 只要避免这一项，这局理论上就能赶上。

如果玩家晚 70 秒：

```text
安检误判 -41秒
冲刺交早 -35秒
```

两项合计 76 秒，则显示：

> **真正拖垮这局的是两个连续判断：安检误判 + 前半程冲刺过早。**

## 31.2 成功局：找出真正救了这一局的操作

假设玩家最终只剩 7 秒：

```text
resultMarginSeconds = +7
```

正向贡献：

```text
提前检查身份证 +28秒
提前靠门        +12秒
最后冲刺        +24秒
```

任何一个贡献如果被拿掉都会让理论结果跌到 0 以下，可以标记为 `decisive: true`。

结算可以写：

> **提前检查身份证真的救了这一局。** 你最终只剩 7 秒，它大约帮你省了 28 秒。

这比只展示“+28秒”更有游戏反馈。

## 31.3 不可控因素怎么写

不可控因素只在以下情况进入前三条：

- 单项损失非常大；或
- 它是这局最大损失；或
- 玩家所有可控选择都表现很好，但仍失败。

推荐文案：

> 地铁临停额外耽误约 1 分 20 秒，这部分你无法避免。

不要用不可控因素教育玩家“下次做得更好”。

# 32. TimeImpact V1.1 数据结构

建议扩展为：

```ts
interface TimeImpact {
  id: string;
  source: string;

  category:
    | "decision"
    | "navigation"
    | "movement"
    | "character"
    | "environment"
    | "operation"
    | "resource";

  // 正数 = 节省 / 追回时间
  // 负数 = 额外损失时间
  deltaSeconds: number;

  avoidable: boolean;
  positive: boolean;

  // 是否与最终成败存在直接因果关系，由结算阶段计算
  decisive?: boolean;

  // 可用于更自然的复盘文案
  displayTemplate?: string;

  characterId?: string;
  eventId?: string;
  decisionId?: string;
  phase?: string;
}
```

约定：

```text
+30 = 相对基准节省 30 秒
-30 = 相对基准损失 30 秒
```

`positive` 可以由 `deltaSeconds > 0` 自动推导，若保留字段则必须校验一致性。

# 33. 主称号优先级：推荐正式规则

建议给称号划分优先级区间，避免以后添加新称号时互相覆盖。

| 优先级 | 类型 | 示例 |
|---:|---|---|
| 1000–1099 | 超稀有特殊结果 | 这都能赶上？、车赶上了裤子没赶上 |
| 900–999 | 极限时间结果 | 最后一秒选手、真就差一秒 |
| 800–899 | 强角色专属 | 身份证去哪了、土特产拖了后腿 |
| 700–799 | 强场景败因 / 胜因 | 栽在安检口、电梯害人 |
| 600–699 | 路线 / 操作表现 | 路线大师、冲刺之神 |
| 500–599 | 高 Drama 结果 | 一路翻车也上了 |
| 400–499 | 一般优秀 / 一般失败 | 从容上车、路线选错了 |
| 0–99 | 默认兜底 | 赶上了、下次早点出门吧 |

同优先级时按以下顺序决胜：

1. `decisive === true`
2. 人物专属 > 通用
3. 条件越稀有优先
4. 若仍相同，使用固定 `tieBreakOrder`

不要随机决定主称号，否则同一局重开结算页可能看到不同结果。

# 34. 副标签生成规则

副标签最多 3 个，不按“满足条件就全显示”。

推荐分为四类：

```ts
type TagType =
  | "positive"
  | "negative"
  | "character"
  | "special";
```

选择规则：

### 成功局

优先顺序：

1. 1 个最关键正向标签
2. 1 个最有戏剧性的标签
3. 1 个角色特色标签

例如：

`#最后冲刺` `#逆风翻盘` `#身份证秒找到`

### 失败局

优先顺序：

1. 1 个 decisive 败因标签
2. 1 个第二大可控错误
3. 1 个角色 / 环境特色标签

例如：

`#走错检票口` `#体力见底` `#翻包48秒`

规则：

- 不要同时显示含义重复的标签，例如 `#体力见底` + `#冲刺交早了`，除非这两个确实都是关键因果。
- 动态数字标签只保留最有意义的一项，例如 `#多跑了210米`。
- 标签应该能在 1 秒内读懂。

# 35. Drama Score 正式计算建议

Drama Score 只衡量“一局有多折腾”，不代表技术水平。

建议基础权重：

| 事件 | Drama + |
|---|---:|
| 小失误 | +5 |
| 走错一次 | +10 |
| 关键路线选错 | +15 |
| 坐反 | +18 |
| 坐过站 | +25 |
| 身份证翻包超过 30 秒 | +15 |
| 孩子临时上厕所 | +12 |
| 孩子尿裤子 | +25 |
| 孩子 PATIENCE 归零 | +20 |
| 电梯等待 > 60 秒 | +12 |
| 地铁临停 > 60 秒 | +10 |
| EN 降到 10% 以下 | +8 |
| 最后 60 秒仍离目标较远 | +15 |

# 36. “预测失败状态”定义

为了支持“逆风翻盘”，游戏过程中可定期计算：

```ts
projectedMarginSeconds =
  currentRemainingSeconds - estimatedRemainingRouteSeconds;
```

如果：

```text
projectedMarginSeconds < -30
```

持续至少一个关键节点，可以记录：

```ts
wasProjectedToFail = true
```

最后成功：

```text
wasProjectedToFail === true && success === true
→ 可触发「逆风翻盘」
```

不要把瞬间 1–2 秒的预测波动算成逆风。

# 41. AchievementConfig 建议改成可序列化配置

如果未来称号 / 成就很多，不建议所有条件都写成散落的函数。

可以使用简单 Rule DSL：

```ts
type CompareOp = "eq" | "gte" | "lte" | "gt" | "lt";

interface Rule {
  field: string;
  op: CompareOp;
  value: string | number | boolean;
}

interface AchievementConfig {
  id: string;
  name: string;
  description: string;
  category: string;
  rarity: AchievementRarity;
  hidden?: boolean;

  all?: Rule[];
  any?: Rule[];

  progressField?: string;
  target?: number;
}
```

例如：

```ts
{
  id: "student_milk_tea_win_3",
  name: "奶茶党",
  description: "买奶茶并成功赶上 3 次。",
  category: "student",
  rarity: "uncommon",
  progressField: "characterStats.student.milkTeaWins",
  target: 3
}
```

特殊复杂条件仍可以使用专门 evaluator，不需要强行把所有逻辑塞进 DSL。

```text
general_first_win
general_win_streak_3
general_win_streak_5
general_last_second
student_milk_tea_win_3
student_id_first_try_5
worker_local_gifts_win
tourist_sleep_no_miss_5
mother_wet_pants_win
family_accessible_route_5
secret_disaster_survivor
```

ID 一旦上线不要因为改文案而修改，否则玩家已有解锁记录会丢失。

---

# 44. 结算页“建议”文案生成

失败结算可以额外生成一句非常短的建议，但只在建议真的明确时显示。

推荐规则：

```text
有 decisive 可控败因 → 显示建议
没有 decisive 可控败因 → 不显示建议
```

示例：

> 如果出门前确认身份证，这局大概率能赶上。

> 你最后差 18 秒；少走一次 B 区折返就够了。

> 前半程少冲一次，把体力留到最后会更稳。

不要生成：

> 下次加油！

> 你可以做得更好！

这类信息量为零的文案。

成功局可以显示“关键操作”，不需要再教育玩家。

# 46. 结算页表现节奏

结算页不要瞬间把全部信息一起显示。

推荐 1.5–2 秒内完成：

```text
0ms
→ 赶上了 / 没赶上

250ms
→ 主称号弹出

500ms
→ 时间 / 距离结果出现

750ms
→ 副标签依次出现

1000ms
→ 原因分析卡片展开

1200ms+
→ 新成就提示
```

动效要求：

- 使用轻微 scale / translate / opacity。
- 不要彩带、烟花铺满屏幕。
- 极限成功可以有一次明显的“呼——赶上了”释放感。
- 失败页保持克制，让称号本身承担幽默感。

---

# 47. 失败原因的公平性要求

为了避免玩家觉得结算在“甩锅”：

1. 只有真实记录过的行为才能成为败因。
2. 不要把理论上不存在的“节省时间”算给玩家。
3. `TimeImpact` 必须在事件发生时记录，不要结算阶段随意估算。
4. 预测值必须标注“约”。
5. 同一损失不能重复记账。

例如：

玩家走错路导致多跑 200 米，并额外花了 50 秒。

只能记录：

```text
走错路线 -50秒
metadata.extraDistance = 200
```

不能同时再记录：

```text
多跑200米 -50秒
```

否则结算会把同一错误算两次。

# 48. 推荐埋点 / 调试数据

即使 V1 没有后端，也建议开发环境记录以下数据，方便后续调平衡：

```ts
interface RunDebugMetrics {
  characterId: string;
  stationId: string;

  success: boolean;
  resultMarginSeconds: number;

  initialTimeSeconds: number;
  actualRunSeconds: number;

  routeEfficiency: number;
  wrongTurns: number;

  voluntaryDelaySeconds: number;
  avoidableLossSeconds: number;
  unavoidableLossSeconds: number;

  sprintContributionSeconds: number;
  finalEnergy: number;

  dramaScore: number;
  primaryTitleId: string;
}
```

试玩后最值得看的指标：

1. 每个人物成功率
2. 成功局平均剩余时间
3. 失败局平均超时时间
4. 每个称号触发率
5. 每个成就解锁率
6. 最大常见败因
7. 玩家是否总在选择同一个开局选项

如果某个称号触发率 > 30%，它通常已经不够像“称号”，需要收紧条件。

如果某个角色 70% 以上失败都来自同一个机制，说明玩法可能过于单一。

# 49. 首轮 QA 测试用例

至少覆盖以下情况：

### Case A：纯净成功

- 0走错
- 无明显负面事件
- 剩余 4 分钟

预期：
- 不出现极限称号
- 可出现“路线大师 / 零失误赶车人”
- 原因分析以玩家优秀操作为主

### Case B：最后 2 秒成功

预期：
- “最后一秒选手”或更高优先级特殊称号
- `#最后冲刺` 等标签合理

### Case C：买奶茶后晚 50 秒

奶茶耗时 120 秒。

预期：
- 奶茶是 decisive 败因之一
- 可触发“奶茶误我”
- 建议指出“不买奶茶理论上足够赶上”

### Case D：买奶茶后晚 4 分钟

预期：
- 奶茶不能被描述成“唯一关键败因”
- 应找更大的路线 / 操作错误

### Case E：地铁不可控临停导致失败

玩家可控操作几乎完美。

预期：
- 可出现“今天不宜赶车”
- 复盘明确标注不可控因素
- 不生成虚假的“下次应该……”建议

### Case F：孩子尿裤子后最后 8 秒成功

预期：
- 主称号优先“车赶上了，裤子没赶上”
- 解锁同名隐藏成就（首次时）
- `#逆风翻盘` 可作为副标签

### Case G：dramaScore 105，剩余 2 秒成功

预期：
- 按产品设定的 priority 决定“这都能赶上？”与“最后一秒选手”的唯一主称号
- 不能随机变化

### Case H：刷新结算页

预期：
- 成就不重复解锁
- lifetime statistics 不重复 +1
- streak 不重复变化

# 50. V1 Definition of Done

结算与成就系统达到以下条件后，可视为 V1 完成：

- [ ] 每局稳定生成且仅生成 1 个主称号
- [ ] 每局最多生成 3 个不重复副标签
- [ ] 成功 / 失败均能生成最多 3 条关键原因
- [ ] 原因分析能区分可控与不可控因素
- [ ] 能识别 decisive 成功贡献 / decisive 失败原因
- [ ] 五个人物均有专属称号
- [ ] 五个人物均有长期成就
- [ ] 至少 5 个隐藏成就可正常触发
- [ ] 成就可持久化到 localStorage
- [ ] 重复打开结算不会重复累计
- [ ] 连胜 / 连续表现统计正确
- [ ] Drama Score 可稳定计算
- [ ] 新成就提示不会阻塞重新开始游戏
- [ ] 结算页在手机竖屏下一屏先看到“结果 + 主称号 + 关键原因”
- [ ] 详细数据折叠或放在第二视觉层级
- [ ] 失败玩家能够一眼看出本局最关键的 1–2 个问题
- [ ] 成功玩家能够一眼看出“自己做对了什么”

# 51. 最终开发原则

这个系统最重要的不是“成就数量多”，而是形成下面这个反馈闭环：

```text
做选择
↓
产生真实后果
↓
赶上 / 没赶上
↓
结算明确告诉玩家关键因果
↓
获得有记忆点的称号 / 成就
↓
玩家知道下一把想尝试什么
↓
再赶一趟
```

只要这个闭环成立，即使 V1 成就数量不多，也会比单纯堆几十个徽章更有重玩价值。
