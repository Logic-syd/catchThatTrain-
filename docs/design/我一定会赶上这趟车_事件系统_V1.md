# 《我一定会赶上这趟车》事件系统设计文档

版本：V1  
范围：通用事件库 + 大学生 / 打工人 / 疲惫游客专属事件  
用途：供产品设计与 Codex 开发实现

---

# 1. 事件系统目标

事件系统的目标不是持续“随机扣时间”，而是制造局面，让玩家自己处理。

核心原则：

- 随机决定“发生什么”
- 玩家决定“怎么处理”
- 角色属性影响处理效率
- 玩家操作影响最终结果
- 同一个事件对不同角色产生不同后果
- 尽量避免事件一触发就直接固定扣时
- 失败应更多来自错误决策、操作失误、资源管理失败，而不是纯 RNG

整体建议：

- 玩家可控制 / 可影响事件：约 70%
- 不可控环境因素：约 30%

---

# 2. 统一事件结构

建议所有事件统一使用配置化结构。

```ts
interface EventConfig {
  id: string

  scope:
    | "common"
    | "student"
    | "worker"
    | "tourist"

  phase:
    | "before_departure"
    | "metro"
    | "transfer"
    | "station_entrance"
    | "security"
    | "concourse"
    | "gate"
    | "final_sprint"

  trigger: EventTrigger

  weight: number

  prerequisites?: EventPrerequisite[]

  title: string
  description: string

  choices?: EventChoice[]

  interactionType?:
    | "choice"
    | "timed_click"
    | "rapid_tap"
    | "swipe"
    | "search"
    | "direction_pick"
    | "queue_pick"
    | "route_pick"
    | "auto"

  statEffects?: StatEffect[]
  timeEffects?: TimeEffect[]

  dramaScore?: number

  tags?: string[]
}
```

建议每个事件至少考虑：

- 触发阶段
- 触发条件
- 玩家是否能主动选择
- 是否有短操作
- 时间收益 / 损失
- AGI / EN / FOCUS / LOAD / FATIGUE 等属性影响
- 是否记录为结算原因
- 是否增加 Drama Score

# 3. 通用事件库

通用事件适用于所有角色。

---

## 3.1 地铁阶段

### 事件 1：车门快关了

触发：
- 到达换乘站或终点站
- 玩家需要下车

表现：

> 到站了！  
> 车门正在关闭……

操作：
- 限时点击【下车！】

结果：
- 成功：正常下车
- 反应慢：多花数秒挤出车门
- 失败：被带到下一站

属性影响：
- FOCUS 越高，判定窗口越长
- AGI 越高，晚一点点击仍有机会成功

Drama：
- 被带过站时显著增加

---

### 事件 2：前方临时停车

触发：
- 地铁行进过程中

表现：

> 前方列车正在等候信号。

选择：

A. 原地等  
- 最稳
- 固定损失一定时间

B. 下一站下车换线  
- 增加路线操作
- 有可能更快
- 也可能更慢

设计目标：
不要直接“随机 -47 秒”，而是让玩家做判断。

---

### 事件 3：下一班还有 4 分钟

触发：
- 进入站台时

选择：

A. 等这班  
- 稳定
- 固定等待

B. 改走另一线路  
- 重新规划
- 可能节省时间
- 增加走错风险

影响：
- FOCUS 高时提供更多路线信息

---

### 事件 4：站台方向看不懂

触发：
- 进入陌生线路
- FOCUS 低时权重更高

选择：

A. 看线路图  
- 消耗时间
- 正确率高

B. 凭感觉选  
- 不耗确认时间
- 可能坐反

结果：
- 选错方向会真正前往下一站后才发现

---

### 事件 5：换乘通道很长

触发：
- 地铁换乘

选择：

A. 冲刺  
- 更快
- 消耗 EN

B. 正常走  
- 稳定
- 保留 EN

这类事件用于强化：
“现在冲，还是把体力留给最后。”

---

### 事件 6：扶梯站满人

触发：
- 换乘通道

选择：

A. 站扶梯  
- 省体力
- 花时间

B. 走楼梯  
- 更快
- 消耗 EN

属性影响：
- AGI 越高，楼梯收益越大
- LOAD 高时楼梯收益下降

---

### 事件 7：地铁很挤

触发：
- 高峰时段 / 高人流线路

选择：

A. 提前往门边挤  
- 需要轻操作
- 到站可快速下车

B. 原地不动  
- 轻松
- 到站后多花时间穿人群

---

### 事件 8：下一站要换乘

触发：
- 到站前

选择：

A. 提前起身靠门  
- 下车更快

B. 继续坐着休息  
- EN 小幅恢复
- 下车较慢

这个事件不需要很戏剧化，但能让玩家持续做事。

---

### 事件 9：临时换站台

触发：
- 低概率环境事件

选择：

A. 跟人流走  
- 快
- 可能被带错

B. 看指示牌  
- 花几秒确认
- 更稳

FOCUS 高时：
- 更容易直接识别正确方向

---

### 事件 10：手机信号差

触发：
- 玩家打开地图或导航

选择：

A. 等加载  
- 消耗时间
- 信息完整

B. 凭记忆走  
- 不等
- 有走错风险

高 FOCUS：
- 凭记忆成功率更高

# 4. 通用进站事件

---

### 事件 11：地铁出口很多

触发：
- 到达高铁站地铁站

表现：

> A口 / B口 / C口  
> 哪个离进站口最近？

玩家：
- 直接选
- 或打开简化地图确认

结果：
- 不同出口对应不同站外距离
- 不是所有出口都一样

---

### 事件 12：入口需要绕行

触发：
- 站外路线

场景：
- 某个入口临时关闭
- 或需要走地下通道

选择：

A. 按指示绕行  
- 稳定

B. 去另一个入口  
- 路线更长但可能人少

---

### 事件 13：入口封了一半

触发：
- 临时施工 / 管制

选择：
- 继续排现有入口
- 去找另一个入口

适合记录为：
- environment
- navigation

---

### 事件 14：行李通道很挤

触发：
- 进入站厅

选择：

A. 普通通道  
B. 宽通道

不同角色最优解不同：
- 大学生偏普通通道
- 重行李角色偏宽通道

### 事件 15：安检队伍选择

触发：
- 安检区

玩家看到：
- A 队：6 人
- B 队：3 人
- C 队：8 人

高 FOCUS 额外信息：
- A：大多轻装
- B：前方大量行李
- C：双通道处理

核心：
“短队不一定快。”

---

### 事件 16：前面有人带很多东西

触发：
- 已经排队后

选择：

A. 继续排  
- 无切换成本
- 但可能慢

B. 换队  
- 先损失一点移动时间
- 有可能整体更快

---

### 事件 17：水瓶没处理

触发：
- 安检

选择：

A. 喝掉  
- 花时间
- 可保留水瓶

B. 丢掉  
- 更快

可与不同角色资源系统联动。

---

### 事件 18：身份证一时没找到

触发：
- 实名核验 / 检票

玩法：
- 翻包小游戏

FOCUS 决定：
- 提示强弱
- 错误位置数量
- 判定时间

这是大学生的高权重专属联动事件，也可以低概率出现在其他角色。

---

### 事件 19：闸机刷不开

触发：
- 进站 / 检票

选择：

A. 再试一次  
- 快
- 可能成功

B. 找人工  
- 稳
- 花时间

---

### 事件 20：检票口临时调整

触发：
- 中后段

表现：

> 广播：G14 次列车检票口调整至 21B。

玩家：
- 看屏幕确认
- 或继续原路线

高 FOCUS：
- 更快意识到变化

# 7. 大学生专属事件库

大学生人物核心：

**最后一秒才出门 + 背书包 + 总觉得还有时间 + 身体条件最好。**

主要矛盾：
- 时间少
- 书包乱
- 自己主动拖延
- 但可以靠冲刺救回来

---

## 7.1 奶茶就在地铁口

表现：

> 地铁口那家奶茶店今天好像不用排队。

选择：

### 买

- 时间 -2:00
- AGI +5
- EN +10
- 前期 sprintRecovery +20%

### 不买

- 无变化

称号关联：
- 奶茶党永不认输
- 奶茶误我

---

## 7.2 要不要先确认身份证

### 现在确认

- 时间 -0:30
- FOCUS +10
- 后续身份证搜索大幅简化

### 肯定在包里

- 不扣时间
- 后续可能触发高难度翻包

---

## 7.3 早餐还没吃

### 买饭团

- 时间 -1:00
- EN +15

### 直接走

- 不扣时间
- 游戏后半段 EN -10

---

## 7.4 耳机掉进包底

触发：
- 地铁准备下车时

选择：

### 找

- 时间 -20～40 秒
- 可正常使用耳机

### 算了

- 无损失

这是轻量氛围事件，不必强制影响后续主流程。

---

## 7.5 手机只剩 15%

选择：

### 充一会

- 时间 -1:30
- FOCUS +5
- 后续地图查看不受电量限制

### 直接走

- 不扣时间
- 后期地图查看时间受限制

---

## 7.6 书包拉链没拉

触发：
- 冲刺后

选择：

### 停下来拉好

- 时间 -15 秒

### 不管

- 当前不扣时间
- 后续有概率掉出物品

属于“现在花小时间 / 留未来风险”的典型事件。

---

## 7.7 身份证去哪了

触发：
- 检票 / 实名核验

玩法：
- 前袋
- 侧袋
- 主袋
- 电脑夹层

FOCUS >= 75：
- 正确位置短暂高亮

FOCUS 55–74：
- 有弱提示

FOCUS 35–54：
- 无明显提示

FOCUS < 35：
- 可出现一次错误怀疑：
  “不会没带吧？”

每翻错一次：
- 时间 -8～12 秒

如果开局已确认身份证：
- 难度大幅下降

---

## 7.8 电脑要不要带

### 带

- LOAD +8
- 安检耗时 +10～15 秒
- FOCUS +5

### 不带

- LOAD 更低
- 移动更轻

---

## 7.9 朋友发消息：“你到了吗？”

### 回

- 时间 -15 秒
- FOCUS +3

### 不回

- 无变化

轻量角色事件。

---

## 7.10 最后两分钟：年轻就是能跑

自动触发：

- sprintSpeed +15%
- EN recovery +25%

这是大学生最重要的后程优势。

# 8. 打工人专属事件库

**实在不想回去上班 + 高 FOCUS + 行李多 + 精神负担重。**

优势：

- LOAD 高
- EN 一般
- 经常被工作消息干扰

# 9. 疲惫游客专属事件库

疲惫游客核心：

**只买到红眼夜班车 + 已经玩了一整天 + 累 + 困 + 不熟路线。**

独有资源：

`FATIGUE`

FATIGUE 越高：

- EN 恢复越慢
- FOCUS 越低
- sprintDuration 越短
- 看路牌反应时间越短

---

## 9.1 买咖啡

### 买

- 时间 -0:50
- FATIGUE -15
- EN +10

### 不买

- 无变化

---

## 9.2 酒店送的两瓶水

### 带

- LOAD +5
- EN +8

### 放下

- LOAD 更低

---

## 9.3 地铁上睡不睡

### 睡

- EN +20
- FATIGUE -20
- 必须设置闹钟

### 不睡

- 不会坐过站
- FATIGUE 继续缓慢上涨

这是游客最核心的主动玩法。

### 1 站前

- 睡得最久
- 恢复最多
- 风险最大

### 2 站前

- 平衡

### 3 站前

- 最稳
- 恢复较少

# 10. 三个人物的事件风格差异

| 人物 | 核心感觉 | 主要事件来源 | 玩家真正管理的东西 |
|---|---|---|---|
| 大学生 | 我还能拖一下 | 奶茶、饭、手机、书包、身份证 | 时间 + 冲刺 + FOCUS |
| 打工人 | 我真不想回去上班 | 土特产、老板、电话、电脑、报销 | LOAD + FOCUS + 工作干扰 |
| 游客 | 我真的太累了 | 困、咖啡、睡觉、闹钟、行李、找路 | FATIGUE + EN + 导航 |

大学生体验：

**很多问题是自己作出来的，但身体条件最好，可以靠操作追回。**

打工人体验：

**身体一般，但信息判断最强，做对决策会非常稳。**

游客体验：

**一直在权衡“现在休息，还是继续赶”。**

# 11. 每局事件数量控制

不要把事件塞得太满。

建议每局：

- 通用事件：3–5 个
- 人物专属事件：2–3 个
- 大环境随机事件：0–2 个
- 核心强制机制：1–2 个

总事件量建议：
约 6–9 个明显事件 / 局

# 13. 事件分类与权重建议

建议事件分为三类。

- 临时施工
- 检票口调整
- 扶梯维修

# 14. 事件触发规则

事件不能完全独立随机。

建议增加：

```ts
interface EventPrerequisite {
  type:
    | "stat"
    | "item"
    | "state"
    | "previous_choice"
    | "phase"
    | "character"
    | "time_remaining"

  key: string
  operator: ">" | "<" | ">=" | "<=" | "==" | "!="
  value: string | number | boolean
}
```

例如：

“土特产袋破了”

必须满足：

```ts
character == "worker"
hasSouvenirBag == true
phase == "station_entrance" || phase == "concourse"
```

“差点睡过站”

必须满足：

```ts
character == "tourist"
isSleeping == true
alarmRisk >= threshold
```

“身份证去哪了”

大学生权重更高：

```ts
character == "student"
checkedIdBeforeLeaving == false
```

---

# 15. 避免重复和连环恶意事件

同一类事件不要连续出现。

例如：

- 刚坐反
- 下一事件又看错方向
- 下一事件又走错检票口

会让玩家觉得系统在故意整人。

建议增加事件冷却：

```ts
cooldownTags: string[]
```

例如：

```ts
tags: ["navigation_mistake"]
cooldown: 2
```

触发一个 navigation_mistake 后：
后两个事件降低同类权重。

---

# 16. Bad Luck Budget

不可控环境损失需要预算限制。

避免：

- 临停
- 施工
- 换检票口
- 扶梯坏
- 又排长队

连续出现导致必输。

建议：

```ts
environmentLossBudget
```

达到预算后：
- 环境负面事件权重下降
- 更多事件转为玩家可控型

---

# 17. 事件结果与结算系统连接

每个重要事件应该写入 `TimeImpact`。

```ts
interface TimeImpact {
  id: string
  source: string

  category:
    | "decision"
    | "navigation"
    | "movement"
    | "character"
    | "environment"
    | "operation"

  deltaSeconds: number

  avoidable: boolean
  positive: boolean

  eventId?: string
}
```

示例：

```ts
{
  id: "student-check-id",
  source: "出门前检查身份证",
  category: "decision",
  deltaSeconds: 28,
  avoidable: true,
  positive: true,
  eventId: "student_check_id"
}
```

这样结算页可以自动分析：

- 奶茶是不是关键败因
- 身份证搜索是不是主败因
- 游客睡觉是不是关键成功原因
- 打工人高 FOCUS 是否真的节省时间
